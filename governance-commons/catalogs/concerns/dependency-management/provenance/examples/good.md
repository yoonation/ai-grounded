# Example: dependency-management.provenance provenance (good patterns)

Substrate-original good-pattern examples for dependency-management.provenance.

## Pattern A: npm provenance verification

```yaml
# .github/workflows/install.yml
- name: Install with provenance verification
  run: |
    npm install --foreground-scripts
    # For packages with Sigstore-backed provenance,
    # verify before allowing in build
    npm audit signatures
```

Why this satisfies dependency-management.provenance (strongest available
provenance): npm provenance attestations (Sigstore-
backed since 2023) bind a published artifact to the
upstream build pipeline (e.g., a specific GitHub Actions
workflow). `npm audit signatures` verifies these
attestations.

## Pattern B: Restricted registry configuration

```ini
# .npmrc - committed to repository
registry=https://npm.internal.example.com/
@example:registry=https://npm.internal.example.com/
audit-level=high
fund=false
```

Why this satisfies dependency-management.provenance (registry control): the
project resolves only against the internal registry,
which proxies and vets public packages. Dependency
confusion attacks are prevented because the internal
registry's namespace cannot be claimed externally.

## Pattern C: pip with hash-checking mode

```text
# requirements.txt - generated by pip-compile --generate-hashes
fastapi==0.104.1 \
    --hash=sha256:752... \
    --hash=sha256:c2c...
sqlalchemy==2.0.23 \
    --hash=sha256:abc... \
    --hash=sha256:def...
```

```yaml
# CI
- name: Install with hash verification
  run: pip install --require-hashes -r requirements.txt
```

Why this satisfies dependency-management.provenance: every package install
verifies the artifact hash against the lockfile;
artifacts with different content are rejected.

## Pattern D: Sigstore verification for container base images

```yaml
# Cosign verification of base image signatures
- name: Verify base image signature
  run: |
    cosign verify \
      --certificate-identity-regexp "^https://github.com/distroless/.+" \
      --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
      gcr.io/distroless/base:nonroot
```

Why this satisfies dependency-management.provenance (extended to container
layer): the base image is verified to be signed by the
expected upstream identity. Substitution attacks at the
registry are detected.

## Pattern E: License extraction and allow-list enforcement

```yaml
# CI step: license check
- name: License compliance
  run: |
    npx license-checker \
      --production \
      --onlyAllow "MIT;Apache-2.0;BSD-2-Clause;BSD-3-Clause;ISC;MPL-2.0" \
      --excludePrivatePackages
```

Why this satisfies dependency-management.provenance (license property): the
license allow-list is enforced mechanically; a
dependency under a non-allow-listed license fails CI.
Substrate-recommended pattern.

## Pattern F: SBOM generation in CI

```yaml
# CI: generate CycloneDX SBOM
- name: Generate SBOM
  uses: anchore/sbom-action@v0
  with:
    format: cyclonedx-json
    output-file: sbom.cdx.json

- name: Sign SBOM with cosign
  run: |
    cosign sign-blob --yes \
      --output-signature sbom.cdx.json.sig \
      sbom.cdx.json

- name: Upload as release artifact
  uses: actions/upload-artifact@v4
  with:
    name: sbom
    path: |
      sbom.cdx.json
      sbom.cdx.json.sig
```

Why this satisfies dependency-management.provenance (SBOM): every build
produces a signed SBOM; downstream consumers can verify
the dependency closure independently.
