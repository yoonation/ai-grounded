# Guidance: Authentication failure responses are generic and time-equivalent across causes

Return a single failure response for all authentication failures, with text like 'Invalid credentials' or 'Authentication failed'. Do not vary based on whether the account exists, the password is wrong, or the account is locked. Ensure timing is uniform. When the account does not exist, still perform a hash verification against a known-bad password hash so the failure path takes the same time as a real password check. Communicate cause to the user only through channels that do not leak to third parties: the password reset flow that emails the registered address (and silently no-ops for unregistered addresses); the account-creation flow that signals 'check your email' for both new and existing addresses. Account lockout signals require careful design. A lockout response that says 'try again in 15 minutes' differs from 'incorrect password'. Substrate guidance: prefer not signaling lockout state in the same response; track lockout server-side and silently reject without rotating the response shape. Login event metrics (which the application logs for security monitoring) can distinguish cause categories because they go to log aggregators not to the user.
