# Guidance: Authentication credentials are not hardcoded as literals in source code

Environment variables: simplest pattern for most applications. Twelve-factor convention. Read at process startup via the language's environment access (os.environ in Python, process.env in Node, System.getenv in Java, os.Getenv in Go). The deployment environment provides the variable from its secrets management. Local development uses .env files outside source control (.gitignore'd) or direnv. Secrets management services: for higher security contexts. AWS Secrets Manager, HashiCorp Vault, Azure Key Vault, Google Secret Manager. The application authenticates to the secrets service (typically via cloud IAM identity, not via stored credentials, achieving zero-bootstrap-credential) and reads secrets at startup or on demand. Allows rotation without redeployment. Encrypted configuration files: ansible-vault, SOPS, git-crypt, age, etc. Credentials are encrypted at rest; decryption keys are managed separately. Hardware secure modules: for highest-security contexts. Private signing keys never leave the module; the application requests signing operations. In all cases the source code reference is the variable or function call, not the value: 'os.environ["DATABASE_PASSWORD"]', not '"actual-password-value"'.
