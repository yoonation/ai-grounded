# SLSA v1.0 Provenance

Specification for SLSA (Supply-chain Levels for Software Artifacts)
provenance attestations generated by consuming frameworks.

## What SLSA Provenance is

A SLSA Provenance attestation records the build that produced an
artifact. It answers:

- **What** artifact was built (digest)
- **Who** built it (the builder identity)
- **When** it was built
- **From what** sources (commit, dependencies)
- **Under what conditions** (build invocation, parameters)

The attestation is structured data (JSON) that can be:

- Generated automatically during CI
- Signed for tamper evidence
- Published to a transparency log
- Verified later by downstream consumers

## SLSA levels

SLSA defines four maturity levels:

| Level | What's required |
|---|---|
| Level 1 | Provenance generated (may be unsigned/unverified) |
| Level 2 | Provenance signed; build runs in hosted build platform |
| Level 3 | Build platform is hardened; provenance is non-falsifiable |
| Level 4 | Two-party review; hermetic builds; out of scope here |

This framework's build-time governance targets **SLSA Level 2** as
the standard. SLSA Level 3 is the future-state goal.

## Provenance schema v1.0

SLSA v1.0 provenance uses in-toto Statement format. The complete
shape:

    {
      "_type": "https://in-toto.io/Statement/v1",
      "subject": [
        {
          "name": "<artifact-name>",
          "digest": {"sha256": "<hex-digest>"}
        }
      ],
      "predicateType": "https://slsa.dev/provenance/v1",
      "predicate": {
        "buildDefinition": {
          "buildType": "<URI identifying the build type>",
          "externalParameters": {
            // Parameters externally controlled (e.g., user inputs)
          },
          "internalParameters": {
            // Parameters set by the builder
          },
          "resolvedDependencies": [
            {
              "uri": "<dep-URI>",
              "digest": {"sha256": "<dep-digest>"}
            }
          ]
        },
        "runDetails": {
          "builder": {
            "id": "<URI identifying the builder>",
            "version": {
              // Builder version info
            },
            "builderDependencies": []
          },
          "metadata": {
            "invocationId": "<unique-id>",
            "startedOn": "<RFC3339 timestamp>",
            "finishedOn": "<RFC3339 timestamp>"
          },
          "byproducts": []
        }
      }
    }

## Field guidance

### `subject`

Array of artifacts this provenance is about. Each subject:

- `name`: Path or identifier (relative path, package name, etc.)
- `digest`: Map of digest algorithm to value. SHA-256 is the
  standard; SHA-512 acceptable.

Multiple subjects allowed when one build produces multiple
artifacts. Each subject is independently verifiable.

### `predicateType`

Must be exactly `https://slsa.dev/provenance/v1` for SLSA v1.0
provenance.

If you have an older `slsa.dev/provenance/v0.2` predicate, that's
the previous schema (significantly different shape). Migrate to v1.0
unless you have specific compatibility requirements.

### `buildDefinition.buildType`

URI identifying what kind of build this was. Examples:

- `https://github.com/Attestations/GitHubActionsWorkflow@v1` for
  GitHub Actions builds
- `https://example.org/builds/python-package@v1` for custom builders

Use a URI you control (not a fake one). Document what the buildType
represents in the URI's documentation.

### `buildDefinition.externalParameters`

Parameters whose values come from outside the trusted build platform.
For GitHub Actions: workflow inputs, event payload. For local builds:
command-line arguments.

These are the parameters an attacker could potentially influence;
recording them lets verifiers detect tampering.

### `buildDefinition.internalParameters`

Parameters the builder itself sets. Includes:

- Builder configuration
- Environment variables set by the platform
- Default values not explicitly provided externally

### `buildDefinition.resolvedDependencies`

Every dependency the build pulled in, with verified digests. This
is the supply chain record:

- Source repositories (git commits with their hashes)
- Package dependencies (PyPI, npm, Cargo, etc. with hashes)
- Container images (with image digests)
- Build tool versions (mise, asdf, system tools)

The more complete this list, the more useful the provenance for
supply chain verification.

### `runDetails.builder.id`

URI identifying the builder. Examples:

- `https://github.com/actions/runner/github-hosted` for GitHub-hosted
  runners
- `https://example.org/builders/local@v1` for local development

The builder identity is what gives the provenance its credibility.
Self-hosted builders should publish their identity URI with build
configuration documentation.

### `runDetails.metadata`

- `invocationId`: Unique identifier for this build run. CI run ID,
  ULID, etc.
- `startedOn` / `finishedOn`: RFC3339 timestamps in UTC

## Examples

### Example 1: Build of a Python package

    {
      "_type": "https://in-toto.io/Statement/v1",
      "subject": [
        {
          "name": "mypackage-1.0.0-py3-none-any.whl",
          "digest": {
            "sha256": "abc123..."
          }
        }
      ],
      "predicateType": "https://slsa.dev/provenance/v1",
      "predicate": {
        "buildDefinition": {
          "buildType": "https://github.com/Attestations/PyPIPackage@v1",
          "externalParameters": {
            "source": "https://github.com/example/mypackage",
            "ref": "refs/tags/v1.0.0"
          },
          "internalParameters": {
            "python_version": "3.12.13",
            "build_tool": "hatch 1.9.0"
          },
          "resolvedDependencies": [
            {
              "uri": "git+https://github.com/example/mypackage@abc...",
              "digest": {"gitCommit": "abc..."}
            },
            {
              "uri": "pkg:pypi/setuptools@69.0.0",
              "digest": {"sha256": "def..."}
            }
          ]
        },
        "runDetails": {
          "builder": {
            "id": "https://github.com/actions/runner/github-hosted",
            "version": {
              "github-runner": "2.311.0"
            }
          },
          "metadata": {
            "invocationId": "1234567890",
            "startedOn": "2026-05-12T10:00:00Z",
            "finishedOn": "2026-05-12T10:02:34Z"
          },
          "byproducts": []
        }
      }
    }

### Example 2: AI-assisted code generation

For builds that include AI-generated code, extend with custom
metadata under `byproducts` or use a separate ai-authorship
attestation (see attestation/README.md).

    {
      "_type": "https://in-toto.io/Statement/v1",
      "subject": [
        {
          "name": "src/feature_foo.py",
          "digest": {"sha256": "..."}
        }
      ],
      "predicateType": "https://slsa.dev/provenance/v1",
      "predicate": {
        "buildDefinition": {
          "buildType": "https://example.org/ai-assisted-edit@v1",
          "externalParameters": {
            "spec": "specs/001-feature-foo/spec.md",
            "spec_digest": "sha256:...",
            "user_prompt": "<redacted>"
          },
          "internalParameters": {
            "ai_tool": "claude-code-1.0.4",
            "ai_model": "claude-opus-4-7",
            "session_id": "01HXYZW..."
          },
          "resolvedDependencies": [
            {
              "uri": "git+ssh://git@github.com/user/repo@<commit>",
              "digest": {"gitCommit": "..."}
            }
          ]
        },
        "runDetails": {
          "builder": {
            "id": "https://example.org/builders/claude-code@v1",
            "version": {"claude-code": "1.0.4"}
          },
          "metadata": {
            "invocationId": "01HXYZW...",
            "startedOn": "2026-05-12T14:30:00Z",
            "finishedOn": "2026-05-12T14:32:15Z"
          }
        }
      }
    }

## Generating SLSA Provenance

Tools that can generate SLSA Provenance v1.0:

- **GitHub Actions**: built-in attestation via `actions/attest-build-provenance`
- **GitLab CI**: `gitlab-runner` v17+ has provenance generation
- **slsa-github-generator**: comprehensive generator
- **Custom**: emit JSON conforming to the schema; sign with cosign

For this framework's build-time use, the recommended path is
GitHub Actions' built-in attestation when running in CI, or
cosign-signed manual generation when running locally.

## Verifying SLSA Provenance

Verification by consumers downstream:

1. Retrieve the provenance attestation alongside the artifact
2. Verify the signature (see cosign-signing.md)
3. Verify the subject digest matches the artifact
4. Verify the buildType matches expectation
5. Verify the builder.id matches expectation
6. (Optional) Verify resolvedDependencies are themselves attested

Tools:

- `cosign verify-attestation` with appropriate flags
- `slsa-verifier` for SLSA-specific verification

## Anti-patterns

- **Provenance without subject digest** — useless; can't verify
  what the provenance is about
- **Wildcard buildType** — vague identifiers prevent meaningful
  verification
- **Missing resolvedDependencies** — supply chain verification
  needs the full graph
- **Build-only provenance for runtime artifacts** — production
  systems need additional attestations beyond build-time
